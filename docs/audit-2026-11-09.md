# PilotPatch office-laptop audit — 9 November 2026

Scope: repeat review of `main` from `6107d46`, followed by fixes prepared as **0.2.2**.
Reviewed Windows setup, locked dependency compatibility, launchers/editor invocation,
diagnostics, project confinement, existing-Edge packaging and the prior audit's
permission/source-sharing/unknown-outcome boundaries. An independent reviewer checked
the changes and reproduced Windows junction, NTFS permission and PowerShell 5.1 cases.
The actual office laptop, its policies and Microsoft account were not accessed.

## Findings and fixes

| Priority | Finding and consequence | Resolution |
| --- | --- | --- |
| P1 | Backend startup imported from the target project's current directory and inherited `PYTHONPATH`. A local `pilotpatch.py` or startup module could run before consent/permissions. | Windows launchers and editor tasks use Python isolated mode (`-I`). Real subprocess tests reject both current-folder and inherited-path substitution. |
| P1 | Python 3.11 lacks `Path.is_junction`; an internal junction could alias an excluded directory such as `.git`. | Inspect `lstat` reparse attributes before resolving any component. A real NTFS junction regression runs without symlink privilege, including the 3.11 API surface. |
| P2 | `doctor` exited 0 despite unavailable chat or required writes; Git presence on PATH did not prove executable/trusted Git. Windows `os.access` also reported writable on a real ACL-denied directory. | Require chat readiness for connected doctor, run Git through the repository's trusted resolution, and create/write/delete one uniquely owned temporary file to verify writes. Read-only mode skips the write probe and reports `null`. |
| P2 | Setup claimed all Python 3.11+, but `pyee==14.0.0` requires 3.12 and locked `pydantic-core==2.33.2` has Windows wheels only through 3.13. | Select supported 64-bit CPython 3.11–3.13, enforce `<3.14` package metadata, use pyee 13.0.1 on 3.11 and 14.0.0 on newer supported versions, and install binary runtime wheels. |
| P2 | Python validation strings and unavailable-version stderr handling failed under Windows PowerShell 5.1's legacy argument/error behavior. Checking only script syntax did not catch this. | Preserve Python literal quoting and catch each failed launcher probe. Three actual PS5.1 bootstrap regressions cover valid Python, version fallback and a broken/copied virtual environment. Full fresh source setup also runs under PS5.1. |
| P2 | The alias batch file forwarded through `CALL`, which reparses arguments; copied virtual environments could fail with confusing install errors. | Launch the interpreter directly from both wrappers; validate an existing environment before installation and explain that it must be recreated on each laptop. |

Python isolated mode follows the [official command-line documentation](https://docs.python.org/3.11/using/cmdline.html#cmdoption-I).
The compatibility correction uses the published [pyee 14 metadata](https://pypi.org/project/pyee/14.0.0/),
[pyee 13 metadata](https://pypi.org/project/pyee/13.0.1/) and
[pydantic-core wheel list](https://pypi.org/project/pydantic-core/2.33.2/#files).
No runtime provider, account/authentication flow or Microsoft endpoint was added.

  3.13**. These are dependency availability checks; only 3.12 executed the full suite

  npm lock audit reported **no known vulnerabilities**.
- Setup, README and office-guide PowerShell command blocks parse. Actual PS5.1
  execution is verified separately from syntax parsing.

## Office acceptance still required

These checks establish local Windows packaging and fixture behavior. They cannot
establish the office laptop's endpoint policy, extension installation permissions,
proxy/TLS access, current authenticated Copilot DOM, account eligibility or live
multi-turn coding behavior. The adapter remains unofficial and supports the public
Copilot hosts in the README, with no Microsoft 365 enterprise connector or fallback.

Use [the office checklist](office-laptop.md) on the actual laptop: create a fresh
environment, run offline doctor, pair its existing Edge profile locally, then run
`login`, connected `doctor` and `probe` separately. Only successful probe verifies a
complete real model reply. An approved disposable-project read/edit/test task remains
the separate coding-workflow acceptance check before confidential work.

Windows 11 x64 is the audited target. Windows 10 and native ARM64 remain unverified;
current [Playwright Windows support](https://playwright.dev/python/docs/intro#system-requirements)
starts at Windows 11 for managed browser/development fixtures. Keep repositories in
ordinary local directories: the preserved reparse-point boundary also rejects some
cloud placeholders. No execution policy, TLS verification or organization control
was disabled, and no real account prompt or repository source was sent to a model.

## Transfer and update

`PilotPatch-Office-0.2.2.zip` contains tracked source, the 0.2.2 wheel and VSIX, a
Windows x64 dependency wheelhouse and SHA-256 file checksums. It excludes virtual
environments, pairing/state, browser profiles and other local artifacts. Python,
Git and Edge must already be installed through the laptop's approved channel.

For an existing installation, stop old PilotPatch tasks yourself, install the updated
backend/VSIX, run `connect`, reload the Edge extension and select the existing Copilot
tab again. The protocol remains 2; regular Edge tabs and Microsoft sign-in stay open.
