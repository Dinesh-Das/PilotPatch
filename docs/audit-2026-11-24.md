# PilotPatch audit, 24 November 2026

The original first-run path depended on a VSIX excluded from Git, a packaging recipe
that installed an unpinned npm tool, two packaging and validation scripts under an
ignored folder, and separate setup steps across PowerShell, VS Code and Edge. A
developer could follow the README from a clean checkout and reach an artifact that
only existed on the original build machine.

## Findings and fixes

| Finding | What changed |
| --- | --- |
| **High.** Build and office-bundle generation were missing from the checkout. | `build.cmd` and its Python builder are versioned. One command builds the wheel, source archive, VSIX, Edge ZIP and Windows offline bundle. Python source, editor contents and packaged Edge files are checked. |
| **High.** Edge required a dropdown selection for one tab. Pairing replacement could asynchronously clear a new selection. | The toolbar shows pairing, opening Copilot or confirmation as appropriate. It highlights a sole eligible tab. The worker serializes pairing changes and binds session selection to that pairing, with explicit confirmation before any bridge authorization. |
| **High.** Managed Windows installation meant reconstructing the Python and VSIX paths. | Setup registers the backend under private user state, uses local wheels when an office bundle is present, and can build and install the VSIX. The Windows bundle resolves locked x64 runtime wheels for Python 3.11, 3.12 and 3.13. |
| **Medium.** The panel reported ready before checking Copilot and sent users to a terminal for every setup instruction. | The panel guides project, backend and Edge setup in order. It copies the two picker paths, reports what it is waiting for and distinguishes a test reply from setup success. |
| **Medium.** Dash-prefixed prompts could be interpreted as CLI flags. The agent audit marked a prompt submitted before the browser had confirmed it. | The editor passes prompts after the argument delimiter. The backend checks chat readiness before collecting task context and records the browser request as an attempt. |
| **Medium.** Git ignores and runtime read filters omitted some local build and pairing state. | Packages, dependencies, local browser profiles and local registration files are excluded. The VSIX and Python wheel package the explicit extension file list. |

## Runtime boundaries reviewed

The CLI and VS Code use the same Python backend. Repository reads pass through the
path guard, ordinary edits have explicit edit policy, command execution follows its
own approval policy and source consent comes before source collection and submission.
Approved commands still run with the user's operating-system permissions.

The existing Edge bridge binds each process to one authenticated tab selection.
It rechecks selection before document injection results can reach the composer and
again before sending. Tests exercise revocation during preparation, distinct turn
completion and unknown outcomes. Recovery still requires checking Edge and the
session when a request was interrupted.

Pair the intended Edge profile only. If the same pairing file is imported into
multiple profiles and each has a confirmed tab, the first profile to connect takes
the process lease. Disconnect the other profiles before working with a different
account.

## Package and installation checks

- A source-only Git snapshot in a path with spaces built all packages with
  `build.cmd --wheelhouse PATH`. Windows x64 runtime wheels resolved for Python 3.11,
  3.12 and 3.13.
- An extracted office bundle passed its SHA-256 check and installed offline under
  Windows PowerShell 5.1 using Python 3.12. `pip check` and `doctor --offline` passed.
- VS Code 1.147.0 installed the VSIX and ran the real Python setup task through
  the registered backend in an isolated editor profile.
- Local Chromium exercised the actual Edge toolbar popup and authenticated bridge.
  The test verified that a two-tab list requires a choice and a sole tab can be
  confirmed directly. The VS Code webview rendered in Edge and passed its layout checks.

## Office acceptance limits

Edge's unpacked extension approval, Microsoft account sign-in and the workplace
policy decision must happen on the intended laptop and profile. The public Copilot
Web adapter depends on visible web controls that Microsoft can change. Microsoft
365 Copilot availability alone doesn't establish adapter compatibility. Microsoft's
personal Copilot service terms contain restrictions on automated access.
[Microsoft Edge extension policies](https://learn.microsoft.com/en-us/deployedge/microsoft-edge-manage-extensions-policies)
[Microsoft Copilot terms](https://www.microsoft.com/en-us/microsoft-copilot/for-individuals/termsofuse)

See the [office acceptance sequence](office-laptop.md) for the device and account
checks before using workplace source.
